# 权限刷新采用「前端重拉 + 重建动态路由」，后端不加刷新接口

权限/角色变更后，前端保留的是登录时的旧快照：localStorage 与 Pinia 里的 `roles` / `permissions` / `menuTree`，以及已注册的动态路由。管理员 A 改了权限，无论刷新浏览器还是重新进入页面，界面仍显示旧菜单、旧按钮、旧路由（新增菜单点进去 404）。用户最初认为需要「刷新后端权限数据」，但核查后端后确认：权限码集合缓存在 Redis `login:user-info:{userId}`（TTL 300s，懒加载），而每次权限点/角色/用户写操作成功后，写路径均已显式 evict 受影响用户的缓存（`evictPermissionUsers` / `evictRoleUsers` / 用户分配角色时 evict 该用户）—— 任何用户下一次请求即自动重建最新权限码。菜单树本身不缓存，每次查库构建。**后端权限数据事实上已经「即时生效」，真正保留旧数据的是前端会话快照与动态路由**。

**决策**：
1. **后端零改动**，不新增任何刷新接口。`GET /user/get/login` 每次查库构建完整 `LoginUserVO`（含最新 `menuTree`），作为前端刷新的现成数据源。
2. **前端新增统一刷新编排** `refreshPermissions()`：重拉 `LoginUser` → 覆盖会话（`session.refreshCurrentUser`）→ **重建动态路由**（移除 `admin-layout` 下全部已注册子路由后按新菜单树重新注册，打破原有一次幂等注册）→ 若当前路由已不在新菜单树中则 `router.replace` 到可访问首页（优先 `/dashboard`）。
3. **两个入口**共用同一编排：手动（顶栏「权限刷新」图标按钮，所有登录用户可见）+ 自动（结构性权限变更成功后：权限点新增/编辑/删除、角色分配权限、角色删除）。
4. **只刷新当前登录者**。其他在线管理员的界面不同步（后端权限码即时正确，界面靠刷新浏览器 / 重新登录 / 手动按钮更新）。

**理由**：后端缓存失效已由写路径保证即时性，再加「刷新接口」是重复机制；真正的缺口在前端 —— 动态路由注册是模块级一次性幂等（`dynamicRoutesRegistered` 标志），没有任何移除/重建能力，导致菜单变更后路由表残留旧记录、新记录不注册。

**被否决的替代方案**：① 后端新增「刷新当前用户权限」接口（清缓存重拉）—— 与写路径 evict 功能重复，无实际增益；② 全局清所有在线用户权限缓存接口 —— 批量 evict 带来 N+1 重建开销，且本次需求只针对当前操作者；③ WebSocket / 轮询同步所有在线管理员界面 —— 需引入推送基础设施与订阅逻辑，超出「手动 + 操作后自动」的需求范围。

**后果**：`registerDynamicRoutes` 的幂等标志需重构为「已初始化 + 可重建」两态，动态子路由批量 `removeRoute` 需按 parent 过滤避免误伤静态路由；`v-permission` 指令仅 `mounted` 评估，刷新后已渲染按钮不会更新，需改为监听 `session.permissions` 响应式重评估；其他在线管理员界面不实时同步，属已知行为；本决策纯前端，不影响双库迁移与后端 schema。
