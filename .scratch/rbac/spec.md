# RBAC 权限控制 —— Spec

Status: done

## Problem Statement

管理后台目前没有任何权限控制：任何能登录的用户都能看到**全部**菜单、调用**全部**管理接口。权限是硬编码的三个枚举角色（`user` / `admin` / `ban`），角色不可配置，无法给不同的管理员分配不同的能力，也无法在运行时调整某个人能看到什么、能做什么。管理后台作为后台系统，需要一套**基于角色的访问控制**：管理员被分配角色，角色拥有菜单/接口/按钮权限点，登录后只能看到有权限的菜单、只能调用有权限的接口。

## Solution

标准三级 RBAC（用户 ↔ 角色 ↔ 权限点）。新增 `role`、`permission` 关联/权限点表，配 `user_role`、`role_permission` 两张关联表。管理后台提供角色管理页（给角色分配权限点树）、权限管理页（运行时维护菜单/按钮/接口权限点树）、用户管理页（给用户分配角色）。后端接口用 `@RequirePermission(权限码)` 注解鉴权，超管角色（`admin`）放行全部。前端登录后根据后端下发的菜单树动态生成路由与侧边栏，按钮用 `v-permission` 指令控制显示。现有 `user_role` 枚举字段与 `UserRoleEnum` 废弃，统一到角色表；封禁归入用户状态。

## User Stories

**登录与菜单可见性**

1. 作为管理员，我登录后能看到被分配角色所对应的菜单，以便只看到我有权限使用的功能。
2. 作为管理员，我看不到未被分配权限的菜单项，以便界面不展示我无法使用的功能。
3. 作为管理员，我直接输入一个我没有权限的页面 URL 时被拦截，以便不通过地址栏绕过菜单访问受限页面。
4. 作为管理员，我登录后的侧边栏菜单层级与排序和权限管理页配置一致，以便导航结构可预期。
5. 作为超管（`admin` 角色），我能看到全部菜单并调用全部管理接口，以便拥有对后台的完全控制。
6. 作为普通后台用户，我登录后至少能看到基础可见菜单（如工作台），以便登录后不至于得到空白页面。

**按钮与操作权限**

7. 作为管理员，我看不到无权限的操作按钮（新增/删除/导出等），以便界面操作与权限一致。
8. 作为管理员，即使页面可访问，我调用无权限的接口也会被拒绝，以便后端兜底、前端隐藏失效也不会越权。

**接口鉴权**

9. 作为超管，我可以调用所有管理接口，以便不受权限点配置限制。
10. 作为未登录访客，我调用管理接口会被拒绝，以便后台接口不对外暴露。
11. 作为被封禁用户，我无法登录后台，以便封禁生效。
12. 作为管理员，当接口权限码无法解析时，该接口默认拒绝而非放行，以便权限失效以"拒绝"为安全默认。

**角色管理**

13. 作为系统负责人，我可以创建、编辑、删除角色，以便维护后台角色体系。
14. 作为系统负责人，我可以给角色分配/取消权限点（菜单/按钮/接口），以便定义该角色能看什么、能做什么。
15. 作为系统负责人，我删除角色时，该角色的用户关联与权限关联被级联清理，以便不留脏数据。
16. 作为系统负责人，我删除仍被用户引用的角色时得到明确提示（需先解绑或确认），以便避免误删导致用户失去权限。
17. 作为系统负责人，我可以启停用角色，以便临时收回一组权限。
18. 作为系统负责人，我可以查看某角色已分配的全部权限点，以便核对权限配置。

**权限管理（权限点树）**

19. 作为系统负责人，我可以在权限管理页运行时新增/编辑/删除菜单节点（标题/路径/组件/图标/排序/父级），以便菜单维护无需改前端发版。
20. 作为系统负责人，我可以维护按钮权限点，以便控制按钮显示。
21. 作为系统负责人，我可以维护接口权限点，以便接口鉴权有据可依。
22. 作为系统负责人，我可以调整菜单排序，以便导航顺序可控。
23. 作为系统负责人，我可以停用某个权限点，以便快速下线某项菜单/按钮/接口能力。
24. 作为系统负责人，删除被角色引用的权限点时得到明确处理（级联清理或阻止），以便不产生悬挂引用。

**用户分配角色**

25. 作为系统负责人，我可以在用户管理页给用户分配一个或多个角色，以便授予其对应权限。
26. 作为系统负责人，我可以查看某用户当前拥有的角色，以便核对。
27. 作为系统负责人，我修改用户的角色后，该用户下次登录即生效，以便权限变更结果可预期。

**登录与会话**

28. 作为管理员，我登录后后端返回我的用户信息、角色集合与权限点树，以便前端据此渲染菜单与按钮。
29. 作为管理员，我登录返回的菜单树与权限管理页配置一致，以便所见即所得。

**数据与迁移**

30. 作为系统负责人，现有 `user/admin/ban` 角色数据迁移到新角色表，以便老用户登录不受影响。
31. 作为系统负责人，MySQL 与 PostgreSQL 两套数据库表结构保持一致，以便双库部署均可运行。

## Implementation Decisions

**数据模型（新增）**

- `role`：角色表，含角色名、角色标识、是否超管标记、启停用状态。
- `permission`：权限点表（单表，`type` 区分 `menu`/`button`/`api`）。`menu` 类型带 `parent_id`（父子层级）、`path`、`component`、`icon`、`sort`、`title`；`button`/`api` 类型带唯一权限码。见 ADR-0001。
- `user_role`：用户↔角色多对多关联表。
- `role_permission`：角色↔权限点多对多关联表。
- 权限码格式：冒号分层 `<模块>:<实体>:<动作>`，如 `system:user:list`、`system:user:delete`。

**迁移与 Seed**

- MySQL 与 PostgreSQL 各新增一条 Flyway 迁移（表结构 + 关联索引）。
- Seed 两个角色：`admin`（超管标记，权限校验直接放行）与 `user`（普通后台用户角色）。
- Seed 初始权限点树：覆盖现有全部管理后台菜单（对照前端导航）与全部管理端接口权限码。
- 迁移现有 `user.user_role` 数据：值为 `admin` 的用户挂 `admin` 角色，其余挂 `user` 角色。
- `user_role` 字段与 `UserRoleEnum` 废弃；`ban` 改用现有 `User.status` 表达封禁。

**后端鉴权**

- 新增 `@RequirePermission(权限码)` 注解，扩展现有 AOP 切面体系；切面从登录用户上下文取权限点集合校验。见 ADR-0002。
- 超管角色放行全部接口校验。
- 登录用户上下文（`LoginUserInfo`）扩展携带角色标识集合；权限点集合在登录时一次性查询（或随会话缓存），避免每次请求查库。
- 管理端接口全面标注权限码，与 seed 权限点一一对应。

**登录与前端数据**

- 登录接口返回聚合：用户信息 + 角色集合 + 权限点树（含菜单与按钮节点）。
- 新增"当前用户权限点树"查询接口，超管返回全量树。
- 前端维护组件标识 → `import()` 映射表（动态菜单的组件来源）。
- 前端移除静态导航注册表，改为根据登录返回的菜单树动态生成路由与侧边栏；路由守卫拦截无权限路径。
- 新增 `v-permission` 指令控制按钮显示。

**管理 API 契约（新增）**

- 角色管理：角色 CRUD、给角色分配权限点树、启停用角色、查询角色权限。
- 权限点管理：权限点树 CRUD（含菜单/按钮/接口三种类型）、排序、启停用。
- 用户管理扩展：给用户分配角色、查询用户角色。
- 上述管理接口本身均需权限码保护。

## Testing Decisions

**好的测试是什么**：只测外部行为 —— 给定入参与登录身份，断言返回结果或抛出的异常；不测实现细节（不测内部缓存命中、不测 SQL 拼接、不测数据库表结构）。安全相关逻辑（拒绝路径）与正常放行路径同等重要。

**测试接缝（三个纯单元测试 seam，无 Spring 容器，沿用现有先例）**：

1. **鉴权切面 seam**：覆盖 未登录 → 拒绝；权限码匹配 → 放行；缺权限码 → 拒绝；权限码不可解析 → 拒绝（延续现有"配置错误默认拒绝"约定，见 ADR-0002）；超管 → 放行。
2. **权限树查询 seam**：构建当前用户权限点树（`parent_id` 递归、排序、启停用过滤、仅可见节点）；多角色权限并集去重；超管返回全量树。
3. **角色/权限管理 seam**：角色 CRUD；给角色分配权限点（整体覆盖、校验权限点存在）；删除角色时 `user_role`/`role_permission` 级联清理；删除被引用权限点的处理。

**先例**：`AuthMigrationTest`、`RedisRateLimiterTest`（无 Spring 容器 + Mockito 静态 mock 的纯单元测试）；`ModulithArchitectureTest` 继续守护新模块的依赖边界。

**不做**：前端自动化测试（前端无测试设施，本 spec 不引入测试框架）；数据库集成测试（双库迁移靠 Flyway 校验，不建容器测试）。

## Out of Scope

- **行级数据权限**（`CONTEXT.md` 已明确本项目不做）。
- **C 端**（app/wxmp/publicapi）的权限控制 —— 仅登录，不接 RBAC。
- 引入 **Spring Security**（见 ADR-0002，沿用自研 AOP）。
- **前端自动化测试框架**的引入。
- 多租户、机构/部门等更复杂的 RBAC 扩展。
- 登录增强（验证码、2FA、SSO）。
- 权限变更的独立审计追踪（不在本 spec 范围内展开）。

## Further Notes

- 双库（MySQL + PostgreSQL）Flyway 迁移必须同步，两套 schema 保持一致。
- 权限码 seed 与接口注解标注必须一致，脱节时接口默认拒绝（ADR-0002 后果）。
- 动态菜单落地后，原静态导航注册表降级为"组件注册表"（ADR-0001 后果），组件标识与 `permission.component` 字段对应。
- 领域术语以 `CONTEXT.md` 为准：权限点、菜单权限/接口权限/按钮权限、权限码、角色、超管、数据权限（不做）。
